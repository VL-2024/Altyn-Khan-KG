# АЛТЫН ХАН — обмен игры с LMS

## 1. Общая схема

В реальном режиме **LMS является источником истины для денежных операций и результата билета**.

1. LMS запускает игру и один раз передаёт стартовые параметры.
2. Игрок выбирает номинал внутри игры из списка доступных номиналов.
3. При нажатии «Новая игра» игра **один раз** вызывает `PayTicket` и покупает один билет.
4. LMS списывает стоимость билета, определяет финансовый результат и возвращает номер `scenario`.
5. Игра программно раскрывает этот сценарий максимум за 3 визуальных броска САКА.
6. Игра показывает выигрыш и баланс, полученные от LMS.

**Отдельные результаты каждого броска LMS не хранит и не передаёт.**

Для всех подобных игр X2 используется принцип:

> LMS хранит только номер `scenario`, а визуальный подвариант бросков генерируется внутри игры программно и детерминированно от `ticketId + scenario`.

Поэтому один и тот же билет при повторном воспроизведении получает тот же визуальный подвариант, но протокол LMS не разрастается полями отдельных бросков.

## 2. Параметры, которые LMS передаёт при запуске игры

После загрузки LMS отправляет игре сообщение `X2_LMS_INIT`.

Пример:

```js
iframe.contentWindow.postMessage({
  type: 'X2_LMS_INIT',
  gameId: 'altyn-khan',
  gameNumericId: 137,
  language: 'RU',
  currency: 'KGS',
  currencyDisplay: 'сом',
  denominations: [25, 50, 100],
  denomination: 50,
  balance: 1255,
  mode: 'real',
  demoAllowed: true,
  demoBalance: 10000,
  session: 'optional-session-id'
}, '*');
```

### Описание параметров `X2_LMS_INIT`

| Параметр | Тип | Обязательный | Описание |
|---|---|---:|---|
| `type` | string | да | Для инициализации всегда `X2_LMS_INIT`. |
| `gameId` | string | рекомендуется | Внутренний текстовый идентификатор игры, например `altyn-khan`. Используется в событиях/аналитике. |
| `gameNumericId` | integer/string | да | Числовой ID игры в LMS. Используется в запросе `PayTicket` как `gameId`. Значение `137` в текущем пакете — dev/fallback и должно быть заменено на фактический ID игры. |
| `language` | string | да | Язык интерфейса, например `RU`, `KG`. Игрок внутри игры язык не меняет. |
| `currency` | string | да | Код валюты, например `KGS`, `RUB`. |
| `currencyDisplay` | string | рекомендуется | Обозначение валюты в интерфейсе: `сом`, `₽`, `$` и т. п. |
| `denominations` | array[number] | да | Список номиналов, доступных игроку внутри игры, например `[25, 50, 100]`. |
| `denomination` | number | нет | **Номинал, выбранный по умолчанию при открытии игры.** Передаётся один раз при запуске. Если не передан, игра выбирает первый элемент `denominations`. |
| `balance` | number | да | Текущий реальный баланс на момент запуска. После `PayTicket` игра использует новое значение баланса из ответа LMS. |
| `mode` | string | да | Стартовый режим: `real` или `demo`. |
| `demoAllowed` | boolean | да | Разрешено ли переключение REAL/DEMO внутри игры. |
| `demoBalance` | number | нет | Начальный виртуальный баланс DEMO, например `10000`. |
| `session` | string | нет | ID сессии, если LMS передаёт его отдельно. Также допускается авторизация через cookie LMS. |

### Важно: `denominations`, `denomination` и `amount` — разные параметры

Например LMS запускает игру так:

```js
denominations: [25, 50, 100],
denomination: 50
```

Это означает:

- игроку доступны `25`, `50`, `100`;
- при открытии выбран `50`;
- игрок может переключиться, например, на `100`;
- при покупке следующего билета игра отправит `amount=100`;
- LMS не должна повторно присылать `denomination=100` после переключения игроком.

`denomination` — только первоначальный выбор при запуске игры.

`amount` — фактически выбранный номинал **конкретного покупаемого билета**.

## 3. Покупка билета / запуск реального раунда

На один билет «Алтын Хан» выполняется **ровно один `PayTicket`**, несмотря на то что визуально билет может раскрываться за 1–3 броска.

Формат запроса:

```http
GET https://dev.superloto.kg/api/Lotto.Users.cls?Method=PayTicket&gameId=137&amount=50
```

### Параметры `PayTicket`

| Параметр | Тип | Обязательный | Кто задаёт | Описание |
|---|---|---:|---|---|
| `Method` | string | да | игра | Для покупки билета всегда `PayTicket`. |
| `gameId` | integer/string | да | LMS | Числовой ID игры, полученный как `gameNumericId` при запуске. |
| `amount` | number | да | игрок / игра | Номинал конкретного билета, выбранный игроком: например `25`, `50`, `100`. |

Если стартовый номинал был `50`, но игрок переключился на `100`:

```http
GET https://dev.superloto.kg/api/Lotto.Users.cls?Method=PayTicket&gameId=137&amount=100
```

Запрос выполняется с `credentials: 'include'`. Если LMS передала отдельный `session`, адаптер также может отправить:

```http
X-Session-ID: <session>
```

## 4. Ответ LMS на `PayTicket`

Минимальный ответ, необходимый игре:

```json
{
  "ticketId": "123456789",
  "scenario": 5,
  "win": 400,
  "balance": 1640
}
```

### Параметры ответа

| Параметр | Тип | Обязательный | Описание |
|---|---|---:|---|
| `ticketId` | string/integer | да | Уникальный номер созданного билета. Используется также как часть детерминированного seed визуального подварианта. |
| `scenario` | integer | да | Номер сценария `1..9`. Именно его LMS хранит как результат визуализации билета. |
| `win` | number | да | Денежная сумма выигрыша по билету. При проигрыше `0`. |
| `balance` | number | да | Актуальный баланс после операции. Игра показывает именно значение LMS. |
| `currency` | string | нет | Код валюты для контроля/отображения. |
| `multiplier` | number | нет | Множитель для дополнительного контроля. Игра может определить его и по `scenario`. |
| `denomination` | number | нет | Может возвращаться, но не является обязательным: стоимость билета уже известна игре как отправленный `amount`. |

Адаптер также умеет нормализовать альтернативные имена полей:

- `ticketId` / `ticket_id` / `id`
- `scenario` / `scenarioId` / `scenario_id`
- `win` / `prize` / `winAmount`
- `balance` / `newBalance`

## 5. Сценарии «Алтын Хан»

Полная математическая серия текущей модели — **50 000 билетов**, RTP = **95%**.

| `scenario` | Результат билета | Множитель | Билетов в серии | Вероятность |
|---:|---|---:|---:|---:|
| `1` | 1–3 чүкө, без выигрыша | ×0 | 15 000 | 30.0% |
| `2` | 4 чүкө | ×0.5 | 12 600 | 25.2% |
| `3` | 5 чүкө | ×1 | 16 450 | 32.9% |
| `4` | 6 чүкө | ×3 | 4 000 | 8.0% |
| `5` | 7 чүкө | ×4 | 1 000 | 2.0% |
| `6` | 8 чүкө | ×5 | 500 | 1.0% |
| `7` | ХАН выбит в 3-м броске | ×10 | 200 | 0.4% |
| `8` | ХАН выбит во 2-м броске | ×15 | 150 | 0.3% |
| `9` | ХАН выбит в 1-м броске | ×20 | 100 | 0.2% |

Итого:

- проигрышных билетов: **30%**;
- выигрышных билетов: **70%**;
- RTP: **95%**.

### Что именно задаёт `scenario`

`scenario` задаёт **итог билета**, а не последовательность координат/бросков.

Например `scenario = 5` означает:

```text
итог: 7 выбитых чүкө
множитель: ×4
```

Визуальный подвариант может быть, например:

```text
1-й бросок: 2 чүкө
2-й бросок: 2 чүкө
3-й бросок: 3 чүкө
итого: 7 чүкө
```

или другой допустимый вариант. Выбор подварианта выполняется **внутри игры** и детерминирован от:

```text
ticketId + scenario
```

LMS не передаёт массив вроде:

```json
{
  "throws": [2, 2, 3]
}
```

и не хранит результаты каждого броска отдельно.

### Сценарии с ХАНОМ

- `scenario = 9` — ХАН должен быть выбит на 1-м броске, билет сразу завершается ×20;
- `scenario = 8` — ХАН выбивается на 2-м броске, ×15;
- `scenario = 7` — ХАН выбивается на 3-м броске, ×10.

До броска с ХАНОМ игра может визуально выбивать обычные чүкө. Эти промежуточные чүкө не меняют денежный итог сценария.

## 6. Связь результата и анимации

Направление и сила броска САКА выбираются игроком:

- тап по САКА запускает бросок;
- САКА можно оттянуть и выбрать направление;
- сила оттяжки влияет на траекторию анимации.

Но это **не RNG и не способ определить выигрыш**.

Финансовый результат уже определён LMS через `scenario` и `win` до визуального раскрытия.

Игра подбирает точку контакта САКА с чүкө/ХАНОМ так, чтобы визуализация соответствовала заранее полученному сценарию.

## 7. REAL / DEMO

- `mode: 'real'` — реальная игра, вызывается `PayTicket`;
- `mode: 'demo'` — демонстрационный режим, реальный `PayTicket` не вызывается;
- `demoAllowed: true` — игрок может переключаться REAL/DEMO;
- `demoAllowed: false` — режим задаётся LMS и переключатель недоступен;
- `demoBalance` — отдельный виртуальный DEMO-баланс.

В текущей DEMO-сборке сценарии идут последовательно с чередованием проигрышного и выигрышного:

```text
1 → 2 → 1 → 3 → 1 → 4 → 1 → 5 → 1 → 6 → 1 → 7 → 1 → 8 → 1 → 9 → повтор
```

Это сделано исключительно для демонстрации всех вариантов игры и не относится к реальному распределению билетов.

---

## 8. Баланс

При запуске LMS передаёт текущий баланс:

```js
balance: 1255
```

После `PayTicket` LMS возвращает актуальный новый баланс:

```json
{
  "balance": 1640
}
```

Игра **не должна считать реальный баланс самостоятельно** по формуле:

```text
старый баланс - номинал + выигрыш
```

Авторитетным является только поле `balance`, возвращённое LMS.

---

## 9. Кнопка `+` возле баланса

При нажатии на `+` игра отправляет родительскому окну событие `X2_GAME_DEPOSIT_REQUEST`.

Общий формат событий адаптера:

```js
{
  source: 'X2_GAME',
  type: 'X2_GAME_DEPOSIT_REQUEST',
  // дополнительные данные игры
}
```

После получения события LMS/host самостоятельно открывает страницу или форму пополнения.

Текущий выбранный номинал может передаваться как информационное поле, но это **не запрос на покупку билета**.

## 10. Основные события игры в сторону LMS

Все сообщения адаптера содержат:

```js
source: 'X2_GAME'
```

### `X2_GAME_READY`

Игра загрузилась и готова принять `X2_LMS_INIT`.

Пример базового сообщения:

```js
{
  source: 'X2_GAME',
  type: 'X2_GAME_READY',
  gameId: 'altyn-khan',
  needsInit: true,
  needsSession: true
}
```

### `X2_GAME_DENOMINATION_CHANGED`

Игрок изменил номинал внутри игры. Это событие можно использовать для аналитики. При покупке билета фактический выбранный номинал всё равно передаётся в `PayTicket` как `amount`.

### `X2_GAME_MODE_CHANGED`

Игрок переключил REAL/DEMO, если это разрешено LMS.

### `X2_GAME_DEPOSIT_REQUEST`

Игрок нажал кнопку `+` возле баланса.

### `X2_GAME_TICKET_READY`

Билет получен от LMS, `scenario` принят и визуальный подвариант подготовлен.

### `X2_GAME_ROUND_COMPLETE`

Визуальное раскрытие билета завершено.

### Ошибки

Ошибки `PayTicket`, отсутствие средств, timeout и ошибки интеграции должны обрабатываться без самостоятельного изменения реального финансового результата игры.

## 11. Сообщения LMS в игру

### `X2_LMS_INIT`

Основная инициализация игры. Передаёт настройки, баланс и режим.

### `X2_LMS_SESSION`

Если session ID появляется или обновляется отдельно:

```js
iframe.contentWindow.postMessage({
  type: 'X2_LMS_SESSION',
  session: 'session-id'
}, '*');
```

Игра сохраняет его и может использовать как заголовок `X-Session-ID` при следующем `PayTicket`.

## 13. Что LMS должна хранить по билету

Минимально для игры достаточно стандартных полей:

```text
ticketId
scenario
win
balance
```

Не требуется добавлять в протокол:

```text
throw1
throw2
throw3
knocked1
knocked2
knocked3
trajectory
impactPoint
```

Все эти данные являются визуальным подвариантом и формируются frontend-игрой.

Это позволяет сохранить единый простой протокол LMS и использовать тот же архитектурный принцип для следующих моментальных игр X2.
