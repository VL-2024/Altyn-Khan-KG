## Главный принцип

**LMS определяет финансовый результат до первого броска.**

На один билет выполняется один `PayTicket`:

```text
PayTicket
   ↓
ticketId + scenario + win + balance
   ↓
AltynScenarioController
   ↓
throw plan 1..3
   ↓
Babylon/Havok визуализирует заранее определённый результат
```

Ни направление броска, ни сила, ни Havok, ни FPS устройства не могут изменить `scenario`, `win` или итог билета.

## Слои

### 1. LMS / Ticket layer

Отвечает только за:

- покупку билета;
- `ticketId`;
- `scenario`;
- `win`;
- новый `balance`;
- номинал, язык, валюту, REAL/DEMO.

**Один билет = один PayTicket.** Три визуальных броска не являются тремя покупками.

### 2. Scenario layer

Файлы:

- `src/scenario-config.js`
- `src/altyn-scenario-controller.js`

Scenario Controller один раз при получении билета строит детерминированный план из:

```text
ticketId + scenario
```

Один и тот же билет должен всегда давать один и тот же визуальный подвариант.

Контроллер определяет:

- сколько всего обычных чүкө должно выйти;
- сколько обычных чүкө выходит каждым броском;
- каким броском выходит ХАН;
- seed каждого броска для выбора конкретных объектов и направлений.

Он **не определяет денежный выигрыш**.

### 3. Throw / Physics layer

Наследуется из Chuko v9.

Отвечает за:

- pointer/touch;
- направление и силу жеста;
- баллистическую дугу САКА;
- попадание сверху в выбранную точку;
- момент контакта;
- Havok-движение;
- визуальный scatter;
- удержание нецелевых объектов внутри игровой области;
- мобильную производительность.

Новое правило Алтын Хан: после каждого броска **не выполняется полный reset раунда**. Из игры удаляются/фиксируются только уже выбитые объекты; остальные чүкө и ХАН остаются в текущем состоянии для следующего броска.

### 4. Round Controller

Новый state machine:

```text
IDLE
  ↓ New Game / PayTicket
TICKET_READY
  ↓
THROW_READY_1
  ↓
FLIGHT → IMPACT → SCATTER → THROW_RESOLVED
  ↓                         ↓ если финал
THROW_READY_2              SETTLED
  ↓
FLIGHT → IMPACT → SCATTER → THROW_RESOLVED
  ↓                         ↓ если ХАН на 2-м
THROW_READY_3              SETTLED
  ↓
FLIGHT → IMPACT → SCATTER
  ↓
SETTLED
```

После `SETTLED` баланс меняется на значение, уже полученное от LMS вместе с билетом.

## Сценарии Алтын Хан

Сохраняем действующие 9 сценариев.

| scenario | Итог | Множитель | Сценарная логика |
|---:|---|---:|---|
| 1 | 1–3 обычных чүкө | ×0 | 3 броска |
| 2 | 4 обычных чүкө | ×0.5 | 3 броска |
| 3 | 5 обычных чүкө | ×1 | 3 броска |
| 4 | 6 обычных чүкө | ×3 | 3 броска |
| 5 | 7 обычных чүкө | ×4 | 3 броска |
| 6 | 8 обычных чүкө | ×5 | 3 броска |
| 7 | ХАН | ×10 | ХАН выходит строго 3-м броском |
| 8 | ХАН | ×15 | ХАН выходит строго 2-м броском |
| 9 | ХАН | ×20 | ХАН выходит строго 1-м броском |

Для сценариев 7–9 обычные чүкө до/вместе с броском ХАНА — только визуальный подвариант. Они не меняют множитель.

---

## Раскрытие обычных сценариев 1–6

Для `scenario 2..6` итоговое количество фиксировано, но распределение по трём броскам меняется детерминированно.

Пример `scenario=5`, итог 7:

```text
билет A: 2 + 2 + 3
билет B: 3 + 1 + 3
билет C: 1 + 4 + 2
```

Для одного и того же `ticketId` вариант всегда одинаков.

`scenario=1` сначала детерминированно выбирает итог **1, 2 или 3**, затем распределяет его по трём броскам.

## Раскрытие ХАН-сценариев

### scenario 9 — ×20

```text
throw 1 → ХАН выходит → конец билета
```

Обычных чүкө вместе с ударом может выйти 0–2.

### scenario 8 — ×15

```text
throw 1 → обычные чүкө
throw 2 → ХАН выходит → конец билета
```

### scenario 7 — ×10

```text
throw 1 → обычные чүкө
throw 2 → обычные чүкө
throw 3 → ХАН выходит → конец билета
```

ХАН до своего назначенного броска должен быть защищён от случайного визуального выхода за границу. Havok может его качнуть/сдвинуть, но `Round Controller` не имеет права зарегистрировать `khanOut=true` раньше `khanThrow`.

## Работа с физикой

Мы сохраняем принцип Chuko v9: **результат детерминирован, движение выглядит физическим**.

На каждом броске Scenario Controller передаёт Throw/Scatter layer:

```js
{
  regularOut: 2,
  khanOut: false,
  seed: '...|throw:1'
}
```

По seed выбираются конкретные ещё не выбитые чүкө. Для них заранее строятся безопасные конечные позиции за игровой границей. Для остальных строятся конечные позиции внутри поля.

Havok используется для контакта, промежуточного движения, вращения и ощущения массы. В конце scatter выполняется visual validation и, если устройство физически пришло к другому состоянию, применяется уже существующий deterministic safety/finalize из Chuko v9.

Это исключает расхождение сценария между iPhone, Android и desktop.

## Объекты раунда

Для Алтын Хан фиксируем:

- **11 обычных чүкө**;
- **1 ХАН**;
- **1 САКА**.

Максимальный денежный обычный сценарий требует 8 из 11 чүкө, поэтому остаётся визуальный запас объектов.

После выбивания объект переносится в `outLayer` и больше не участвует в следующих бросках текущего билета.
