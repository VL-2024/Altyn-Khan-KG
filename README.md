# X2 LOTO — ЧҮКӨ Modern 3D

## Назначение сборки

`ЧҮКӨ Modern 3D` — браузерная 3D-игра X2 LOTO на Babylon.js + Havok. Сборка предназначена для размещения на сайте X2 LOTO и подключения к LMS.

Ключевой принцип REAL-режима: **LMS является единственным источником истины для билета, сценария, выигрыша и итогового баланса.** Игра не рассчитывает денежный выигрыш самостоятельно. После получения билета от LMS клиент только визуализирует выданный сценарий.

Текущая интеграционная схема уже реализована в коде:

- статическая HTML/JS-игра, которую удобно размещать отдельным URL и открывать в `iframe`;
- инициализация через `postMessage` (`X2_LMS_INIT`);
- получение session от родительской страницы;
- покупка билета через LMS `PayTicket`;
- REAL / DEMO;
- номиналы;
- баланс;
- локальная история последних билетов;
- автоигра;
- RU / EN / KG / ZH;
- события игры в родительское окно;
- адаптация под desktop / iPhone / Android / in-app browsers.

> Полное ТЗ программисту и порядок подключения: **`INTEGRATION_INSTRUCTION.md`**.  
> Формальный контракт LMS: **`LMS_API.md`**.  
> Краткий чек-лист работ: **`PROGRAMMER_TASK.md`**.

## Сценарии

Игра поддерживает полный набор сценариев от `0` до `5` выбитых обычных чүкө, а также варианты с ХАНОМ для каждого выигрышного количества от `1` до `5`.

Numeric ID `1..7` сохранены без изменений для обратной совместимости с уже настроенной LMS-интеграцией. Новые варианты `+ ХАН` добавлены новыми ID `8..11`.

| ID | Ключ | Визуальный результат |
|---:|---|---|
| 1 | `ZERO` | выбито 0 |
| 2 | `ONE` | выбито 1 чүкө |
| 8 | `ONE_KHAN` | выбито 1 чүкө + ХАН |
| 3 | `TWO` | выбито 2 чүкө |
| 9 | `TWO_KHAN` | выбито 2 чүкө + ХАН |
| 6 | `THREE` | выбито 3 чүкө |
| 10 | `THREE_KHAN` | выбито 3 чүкө + ХАН |
| 7 | `FOUR` | выбито 4 чүкө |
| 11 | `FOUR_KHAN` | выбито 4 чүкө + ХАН |
| 4 | `FIVE` | выбито 5 чүкө |
| 5 | `FIVE_KHAN` | выбито 5 чүкө + ХАН |

### DEMO: случайный выбор сценария

Начиная со сборки **0.13.21**, в обычном DEMO сценарии **не идут по кругу**. При каждом создании нового DEMO-билета сценарий выбирается заново случайно по весам из `src/scenario-config.js`.

| Сценарий | Вероятность в DEMO |
|---|---:|
| `ZERO` | **20%** |
| `ONE` | 8% |
| `ONE_KHAN` | 8% |
| `TWO` | 8% |
| `TWO_KHAN` | 8% |
| `THREE` | 8% |
| `THREE_KHAN` | 8% |
| `FOUR` | 8% |
| `FOUR_KHAN` | 8% |
| `FIVE` | 8% |
| `FIVE_KHAN` | 8% |

Итого: `ZERO` выпадает в среднем в **20%** DEMO-игр, оставшиеся 10 сценариев делят остальные 80% поровну.

Вес задаётся полем `demoWeight` у каждого сценария. Это позволяет менять DEMO-частоты без изменения основной игровой логики. Сумма весов сейчас равна 100, но алгоритм нормализует любые положительные веса автоматически.

Принудительный QA-параметр `?scenario=` имеет приоритет над случайным выбором. Например `?scenario=ONE_KHAN` всегда создаст именно `ONE_KHAN`.

Функция `demoAt()` и массив `demoOrder` сохранены только как служебный/QA-порядок справочника и **не используются для обычного случайного DEMO**.

### Важное правило по выплатам

Поле `demoMultiplier` используется **только для локального DEMO/QA** и не является утверждённой таблицей выплат.

Для REAL-режима:

- LMS заранее определяет `scenario`;
- LMS возвращает точный `win`;
- игра не вычисляет денежный выигрыш из количества выбитых чүкө или наличия ХАНА;
- итоговый денежный результат всегда берётся из ответа LMS.

То есть любой из 11 сценариев — это только визуальное описание результата билета, а не формула выплаты.

## REAL: главный цикл раунда

1. LMS/родительская страница инициализирует игру.
2. Игрок выбирает номинал.
3. По кнопке «Новая игра» игра делает `PayTicket`.
4. LMS возвращает `ticketId + scenario + win + balance`.
5. Игра сохраняет `balance` как pending и получает право начать бросок.
6. Игрок бросает САКА.
7. 3D визуализирует сценарий.
8. После завершения анимации показываются `win` и точный `balance`, возвращённый LMS.
9. Игра отправляет `X2_GAME_ROUND_COMPLETE` родительской странице.

Важно: при REAL билет должен быть создан **до броска**, потому что результат уже определён LMS и затем только визуализируется.

## Баланс

Баланс приходит:

- первый раз в `X2_LMS_INIT.balance`;
- затем в каждом ответе `PayTicket`;
- и, для поддержания LMS-сессии между раундами, из периодического
  `Method=Balance` (см. «Синхронизация с Mahjong Luck» ниже).

При нажатии «Новая игра» UI оптимистично уменьшает отображаемый баланс на стоимость билета. Если покупка билета не состоялась, сумма возвращается. После завершения раунда устанавливается точный `balance` из ответа LMS.

## Синхронизация с Mahjong Luck / Upay / ЧҮКӨ-ОРДО (единый контракт по всей линейке X2 LOTO)

Портированы фиксы/фичи, уже сделанные в этих играх (та же общая
X2-интеграция):

- **Авторизация — через cookie (`sessionMode: 'cookie'`), не токен.**
  Решение всей команды (2026-09) — было принято ещё во время работы над
  Mahjong Luck, но в этой игре `lms-config.js` до сих пор был на
  `sessionMode: 'postMessage'`. `credentials: 'include'` в
  `apiRequest()` уже был на месте (эта игра в этом плане была впереди
  сестринских — просто конфиг не переключили). **Условие:** домен игры
  должен совпадать с доменом сайта LMS — иначе браузер (Safari ITP,
  SameSite) не пришлёт cookie в кросс-доменном iframe.
- **`scenario` в ответе PayTicket — массив `[id, 0]`**, не голое число.
  `normalizeTicket()` теперь читает первый элемент массива перед
  передачей в `scenarioCfg.get()` — раньше `scenarioCfg.get([3,0])`
  превращалось в `Number([3,0])` → `NaN` → билет всегда отклонялся бы
  как `BAD_SCENARIO_RESPONSE`, если бы реальный бэкенд когда-нибудь
  прислал именно такой ответ.
- **Keep-alive для LMS-сессии, наконец подключён.** `X2LMS.getBalance()`
  уже существовал в `lms-adapter.js`, но **нигде не вызывался** — теперь
  `startBalancePolling()` в `src/game.js` дёргает его раз в ~5 минут
  (`LMS_CFG.balancePollIntervalMs`), только пока вкладка видима и
  розыгрыш не идёт (`gameState.phase === 'idle' || 'settled'`). Заодно
  исправлен сам `getBalance()`: раньше он бил в отдельный REST-путь
  `cfg.endpoints.balance` (`/api/lms/player/balance?currency=...`),
  которого на реальном бэкенде не существует — теперь `Method=Balance`
  идёт на тот же `cfg.endpoints.newGame`, что и `PayTicket`, с
  `idIG`/`idSK` и разбором ответа `{Accounts:[{Balans,Currency,...}]}`,
  как подтверждено бэкендом для остальных игр линейки. LMS подтвердила:
  любой авторизованный запрос сбрасывает 15-минутный таймаут
  неактивности сессии — без этого поллинга игрок, отвлёкшийся дольше 15
  минут, мог бы упереться в протухшую сессию на следующем `PayTicket`,
  хотя его логин на сайте живёт 30 дней.
  **Открытый вопрос к бэкенду:** нужен ли `idIG` для `Method=Balance`,
  или (как и `PayTicket`) достаточно cookie-сессии — игра сейчас `idIG`
  никак не получает. См. `LMS_API.md` §4.
- **Авторские права** (невидимо игроку) — `<meta name="copyright">` +
  комментарий в `<head>` `index.html`, и по одной строке в начале
  `src/game.js`, `lms-config.js`, `styles.css`.

## Быстрый запуск QA

Текущая сборка имеет локальный mock-режим. Для автономного теста достаточно раздать папку обычным HTTP-сервером (не открывать `file://`).

Для принудительного сценария QA поддерживается query-параметр `scenario`, например:

```text
?scenario=ZERO
?scenario=ONE_KHAN
?scenario=TWO_KHAN
?scenario=10
?scenario=FIVE_KHAN
```

Для production mock необходимо отключить — см. `INTEGRATION_INSTRUCTION.md`.

## Перед production обязательно

- `mock: false`;
- реальный `gameId` в `lms-config.js`;
- реальный URL `PayTicket` (`cfg.endpoints.newGame`);
- **домен деплоя игры должен совпадать с доменом сайта LMS** —
  `sessionMode: 'cookie'` не пришлёт cookie в кросс-доменном iframe;
- ограничить `parentOrigin` / `allowedParentOrigins` конкретными origin
  (сейчас `['*']` — открыто только для теста);
- проверить CORS / cookies / session header;
- уточнить у бэкенда `idIG`/`idSK` для `Method=Balance` (см.
  «Синхронизация с Mahjong Luck…» выше и `LMS_API.md` §4);
- решить, оставляем ли DEMO;
- скрыть/удалить FPS-панель и debug-строку, если они не нужны оператору;
- унифицировать номер версии во всех файлах перед релизом;
- не показывать игроку сырые технические коды из `X2_GAME_ERROR`.

## Важное правило по ошибкам

`X2_GAME_ERROR` — канал технической интеграции и телеметрии. Родительский сайт **не должен** показывать игроку `code`, `message`, stack trace или внутренние коды напрямую.

Игроку показываются только нормальные локализованные сообщения интерфейса игры: недостаточно средств, сессия завершена, не удалось начать игру и т.п.

В частности, внутренние визуальные диагностические проверки не должны становиться пользовательскими ошибками. LMS-результат билета остаётся авторитетным.


## Обновление на Samsung / Android и кэш браузера

Сборка **0.13.21** содержит принудительное cache-busting для локальных JS/CSS и самого HTML.
При первом открытии URL автоматически добавляется `?build=0.13.21`. Это сделано потому, что Samsung Internet и ярлык сайта на домашнем экране могут продолжать использовать старый `index.html`, даже если файлы на сервере уже заменены.

После выкладки новой версии программист должен:

1. заменить **весь комплект файлов**, а не только `scenario-config.js`;
2. убедиться, что `index.html` содержит ссылки вида `?v=0.13.21`;
3. открыть игру один раз по новому URL с `?build=0.13.21`;
4. если на устройстве сохранён старый ярлык сайта, удалить его и создать заново после первого открытия новой сборки.

Проверка версии: файл `BUILD.txt` и глобальная переменная `window.X2_CHUKO_BUILD` должны показывать `0.13.21`.


## Scenario order / DEMO weights — authoritative

Numeric ID остаются совместимыми с прежним LMS: `1=ZERO, 2=ONE, 3=TWO, 4=FIVE, 5=FIVE_KHAN, 6=THREE, 7=FOUR, 8=ONE_KHAN, 9=TWO_KHAN, 10=THREE_KHAN, 11=FOUR_KHAN`.

`demoOrder` задаёт только стабильный порядок справочника/QA и не должен определяться сортировкой numeric ID.

Обычный DEMO использует `randomDemo()` и поля `demoWeight`: `ZERO=20`, все остальные сценарии `=8`. Поэтому каждый новый DEMO-билет выбирается независимо и случайно, а не как следующий элемент цикла.


## Samsung / Android: отображение ХАНА

Начиная со сборки **0.13.20** итоговый пользовательский результат после завершения раунда берётся из авторитетного сценария LMS (`regular` + `khan`), а не повторно вычисляется по screen-space проекции 3D-модели. Это устраняет устройство-зависимую ошибку, когда визуально ХАН уже находится за ковром, но Samsung Internet из-за отличий viewport/projection мог показывать «ХАН УСТОЯЛ».

Функция визуальной проверки (`visualScenarioResult`) сохранена только как диагностическая: она может записать несовпадение в console при включённом debug, но не меняет результат билета и не показывается игроку.
